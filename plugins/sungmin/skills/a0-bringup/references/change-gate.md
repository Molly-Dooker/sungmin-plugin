# skills 변경 관문

aviron-skills 플러그인을 바꾸는 모든 작업에 적용한다. 검토사항을 만들 때, 개선안을 짤 때, 구현할 때 모두 해당한다. 운영 문서만 고치는 일에는 적용하지 않는다.

이 기준이 생긴 배경(042차, 11-04): 0.42.0 작업분이 run 검증 하나 없이 v0.41.1 대비 +4,820줄, 새 파일 8개로 커졌다. 범위를 점검해 약 3,700줄을 다시 뺐다(sungmin 저장소 `aviron-skills/rounds/042/3_개선안ver3.md`). 이 지침은 같은 일이 되풀이되지 않게 하는 것이 목적이다.

## 언제 보나

- 검토사항 항목을 개선안(ver0)에 올릴 때 항목마다 아래 다섯 칸을 채운다.
- 구현 직전에 다시 본다.
- 구현하다가 계획보다 커지면 멈추고 다시 본다. 커진다는 것은 새 파일, 새 기록 필드, 새 checker 규칙, 새 stage 산출물, 새 모드나 옵션, 새 백업·중간 단계가 생기는 경우다.
- 칸을 채우지 못하거나 판정이 아래 기본값과 다르면 구현하지 않고 사용자에게 묻는다.

## 다섯 칸

| 칸 | 묻는 것 |
|---|---|
| 근거 | 몇 run에서 몇 건이었나. 장치나 산출물로 확인한 것과 추정을 나눈다 |
| 결함 종류 | 지침이나 구조의 결함인가, 아니면 같은 지침에서 에이전트가 run마다 다르게 짠 실수인가. 다른 run이 같은 지침으로 맞게 했다면 실수다 |
| 수정 성격 | 원인을 고치는가, 증상을 검사하는가. 이번에 보인 모양만 잡는지, "사고 하나에 checker 규칙·기록 필드·시험 하나"인지, 에이전트가 직접 적은 기록끼리만 대조하는지 본다 |
| 규모와 run 부담 | 줄 수, 새 파일. run마다 에이전트가 새로 써야 하는 파일과 기록, 다시 돌려야 하는 것, 장치 시간. 발동하지 않는 run도 내야 하는 비용. 등록 모델에서 실제로 동작하는지 |
| 관계 | 진행 중이거나 기록된 구조 수정(예: 042 L15, generator가 참조 runtime 재사용)이 들어오면 필요 없어지거나 바뀌는가. upstream(tenstorrent skills, tt-transformers, vllm-tt-plugin)에 같은 일을 하는 것이 있는가, 아니면 BOS 전용 장치인가 |

## 기본 판정

- **먼저 놓친 이유를 확인한다:** 항목을 판정하기 전에, 계약·기록·리뷰 가운데 그 결함을 잡았어야 할 장치가 있는지 본다. 있으면 왜 놓쳤는지(어느 기록이 흡수했는지, 비교할 기준이 없었는지, 리뷰 문장이 없었는지)를 산출물로 확인한다. 놓친 이유가 지침 쪽이면 실수 한 건이 아니라 규칙의 빈칸이다(045 044-9: 3B pad 21 ms가 `ttft_accounting`의 층 밖 시간에 흡수돼 gap이 −1.6 ms로 지나감).
- **에이전트 실수 한 건:** 위 확인에서 지침 쪽 빈칸이 없을 때만 이렇게 판정하고, skills를 바꾸지 않는다(042 L6). 용어가 모호해서 생긴 실수면 정의 문장 하나만 고친다(042 L5).
- **known_defects 행과 기록 문장은 후조치다:** 다음에 같은 증상이 났을 때 진단을 돕는 참조일 뿐이다. 에이전트는 실패를 분류할 때만 known_defects를 보므로, 느리지만 정상으로 도는 결함은 막지 못한다. 그것만으로 항목을 닫지 않는다. 위 확인을 거쳐 사전 차단(계약·리뷰 문장)이 필요한지 따로 판정하고, 둘을 함께 쓸 수 있다.
- **규칙이 없어서 생긴 결함:** 계약이나 리뷰 문장으로 고친다. checker는 넣지 않는다(042 L3).
- **checker 규칙:** 아래 셋이 모두 맞을 때만 넣는다.
  - 지침·구조·계약에 결함이 있다.
  - 규칙이 이번 모양이 아니라 기전에서 나와 모든 모델에 그대로 적용된다(042 L10, `minimal_matmul`의 `M > N` grid 뒤집힘).
  - 에이전트가 적은 기록이 아니라 산출물 자체로 판정할 수 있다.
- **근거 없는 중간 단계·모드·필드:** 넣지 않는다(042 L4 `first_last`·`sensitive`·`marginal`, O2 `eligible`). 근거가 있는 한 단계만 넣고, 다음 run에서 모자라면 그때 더한다.
- **발동하지 않는 run도 비용을 내는 장치:** Stage 2 사전 준비, 바꿀 때마다 다시 돌리기, 최신성 gate 같은 것이다. 그 비용을 근거와 함께 따로 적고 사용자 확인을 받는다.
- **모델마다 에이전트가 새로 짜는 코드:** 시험 harness로 둘러싸기 전에 공용 코드나 참조 코드로 옮길 수 있는지 먼저 본다(042 L1 1단계를 빼고 L15로 넘김).
- **참조 코드의 결함:** 참조(aviron-transformers)를 고치고 장치로 확인한다. skills에서는 gitlink와 문장만 바꾼다(042 L12).
- **run 검증 없이 쌓인 변경:** 다음 변경에 들어가기 전에 run으로 검증하자고 먼저 제안한다.

## 기록

- 개선안의 항목마다 다섯 칸과 판정을 남긴다. 판정은 반영, 문장만, 반영 안 함, 구조 수정과 함께 중 하나다. "실수 한 건"이나 "반영 안 함"으로 둔 항목에는 놓친 이유를 확인한 결과를 한 줄 적는다.
- 구현 기록(`3_개선안verN.md`)에는 commit별 줄 수, 새 파일, run 부담을 적는다.
- 판정이 기본값과 다르면 그 이유와 사용자 결정을 적는다.
